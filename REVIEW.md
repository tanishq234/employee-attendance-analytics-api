# REVIEW.md

Review of the starter `app/main.py` (the version shipped in the candidate kit).
Every row below was reproduced against the starter before it was changed; the
"how you'd notice it" column is the actual input or test that shows it. The
regression tests live in `tests/` and are named in the last column where a
single test pins the fix.

## Confirmed defects

| # | Where | What is wrong | How you'd notice it | How it is fixed |
|---|---|---|---|---|
| 1 | `health()` | Returns `{"status": "ok"}` unconditionally; MongoDB is never contacted. | Stop MongoDB and `GET /health` — still 200. The contract requires 503, and the grader polls this before testing. | `health()` runs `client.admin.command("ping")` and raises 503 on a driver error. It also retries index creation if the database was unreachable at startup. `test_health_is_ok_when_mongodb_answers` |
| 2 | module level | No indexes are ever created, although the contract says "create all indexes at startup, idempotently" and the seeded database has only `_id`. | `db.attendance_logs.getIndexes()` after startup shows one index. Every list and analytics query is a collection scan, and the 409 guarantees in #4 and #10 are impossible. | `INDEX_PLAN` + `ensure_indexes()`, called from the `lifespan` handler. `create_index` is a no-op when the index already exists, so it is safe on a pre-seeded database. |
| 3 | `MongoClient(...)` | Built without `tz_aware`, so PyMongo hands back **naive** datetimes, which are then mixed with the IST-aware datetimes the helpers build. No pool size or timeouts either. | `compute_overtime()` subtracts a naive `punch_out` from an aware `end`: `TypeError: can't subtract offset-naive and offset-aware datetimes` → HTTP 500. | Client is created with `tz_aware=True`, `maxPoolSize`, and connect/server-selection/socket timeouts. `as_utc()` additionally normalises any naive datetime as UTC. `test_naive_datetime_is_treated_as_utc` |
| 4 | `create_employee()` | `find_one()` then `insert_one()` — a check-then-insert race, with no unique index behind it. | Fire 8 identical `POST /employees` in parallel: several get 201 and the collection ends up with duplicate `emp_code` values. | Unique index `uniq_emp_code`; the insert is attempted directly and `DuplicateKeyError` becomes the 409. `test_parallel_employee_creates_give_exactly_one_201` |
| 5 | `create_employee()` | `datetime.now()` is naive **local** time, so on an IST machine `created_at` is stored 5h30m ahead of the real instant. | Create an employee and read the raw document: the BSON date is 05:30 in the future relative to `date -u`. | `now_utc_truncated()` returns aware UTC, truncated to whole seconds per R1. |
| 6 | `create_employee()`, `list_employees()`, `punch_in()`, `list_attendance()` | Documents are returned as-is, so instants go out as BSON datetimes (serialised as ISO strings) instead of integer epoch milliseconds. | `POST /employees` returns `"created_at": "2026-07-06T18:30:00"`; the contract requires `1783...000`. | `employee_out()`, `attendance_out()` and `history_entry_out()` are the single serialisation path; every instant goes through `datetime_to_epoch_ms()`, including the ones nested inside `history[].changes`. `test_create_employee_returns_201_and_epoch_created_at` |

| 10 | `list_employees()` | No sort, although the contract says `emp_code` ascending. Order is whatever MongoDB returns. | Insert `EMP0003`, `EMP0001`, `EMP0002` in that order and the list comes back in insertion order. | `.sort([("emp_code", ASCENDING)])`, served by the `dept_emp_code` index when a department is given. |
| 11 | `list_employees()`, `list_attendance()` | `page` and `page_size` are plain `int`s: `page=0`, `page=-5` and `page_size=10000` are all accepted (R10 caps `page_size` at 100). | `?page_size=1000` returns 1000 items; `?page=0` returns a nonsense window. | `Query(ge=1)` / `Query(ge=1, le=100)`, so FastAPI returns 422. `test_invalid_pagination_is_422` |
| 12 | `punch_in()` | The result of `find_one` is never checked for `None`, and the code then does `emp["shift_start"]`. | `POST /attendance/punch-in {"emp_code": "EMP9999"}` → `TypeError: 'NoneType' object is not subscriptable` → **HTTP 500**. ## Examined and decided they are **not** defects

* **`load_dotenv()` at import time.** `python-dotenv` does not override variables that are already set, so the values the grader injects win over a local `.env`. Kept as-is; the contract explicitly allows a local `.env`.
* **`IST = timezone(timedelta(hours=5, minutes=30))`.** The offset is right and India has never observed DST, so a fixed offset is correct here and a tz database dependency would buy nothing.
* **Creating the `MongoClient` at module level.** PyMongo connects lazily and the client is thread-safe with its own pool, so this does not need to move into a startup hook and does not delay the port binding. Only its *options* were wrong (#3).
* **`find(q, {"_id": 0})` in `list_employees()`.** This one projection does correctly keep `_id` out of the response — unlike `punch_in()` and `list_attendance()`, which re-add it as `id` (#19, #27). I replaced it with an explicit serialiser anyway, so that the response field set is pinned in one place rather than relying on a projection.
* **`doc.pop("_id", None)` in `create_employee()`.** `insert_one` mutates the dict it is given, so this really does strip the generated `ObjectId` before the response is built. It is not a leak; the problem in that handler is the shape of `created_at` (#6).
* **The inclusive `$gte`/`$lte` date range in `list_attendance()`.** The bounds match the contract ("`date_from`/`date_to` are inclusive"), and comparing `YYYY-MM-DD` strings is a correct ordering, so string dates need no conversion. Kept, and reused by `/admin/explain/attendance_list`.
* **Returning `work_hours: None` and `late_minutes: 0` on a fresh punch-in.** That is exactly what `DATA_MODEL.md` prescribes for a presence record with no punch-out yet, so the starter's defaults were right.
